# Windows packaging for a PySide6 Frontdoor

**Research date:** 2026-11-13
**Question:** What should the Windows V1 packaging and release-candidate path use?

## Recommendation

Use Qt for Python's `pyside6-deploy` to freeze the PySide6 frontdoor. Qt describes it as its recommended deployment tool; it wraps Nuitka. Configure `standalone` explicitly and commit the generated `pysidedeploy.spec`. The tool's default output is a Windows `.dist` directory containing the executable and its runtime files; `onefile` is optional. The default mode changed in Qt for Python 6.12, so relying on the default would make builds version-sensitive. [Qt deployment overview](https://doc.qt.io/qtforpython-6/deployment/index.html) · [pyside6-deploy reference](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html)

For the first release candidate, deliver a **portable ZIP** of the standalone `.dist` directory with a short README, version/build identifier, and SHA-256 checksum. This is a recommendation based on Qt documenting ZIP and frozen-directory distribution as supported artifact shapes. It is not an MSI installer or an auto-updater; Qt's frozen-app deployment tools do not provide update functionality. Decide on an MSI only after the portable artifact and install/setup path work on a clean Windows machine. [Qt deployment overview](https://doc.qt.io/qtforpython-6/deployment/index.html)

## Repeatable build inputs

Keep the user-facing package metadata separate from a Windows packaging lock. The lock should specify Python version and architecture, exact versions and hashes for PySide6 and all build/runtime dependencies, plus the Nuitka toolchain inputs. Python's packaging guidance distinguishes broad project dependency declarations from environment-specific pinned requirements. Install the lock with pip hash checking (`--require-hashes`) and binary wheels only, then run `pyside6-deploy --no-install` using the checked-in deployment spec. Qt documents `--no-install` for environments where dependencies are already installed, and recommends committing the spec because it records deployment settings. [PyPA dependency guidance](https://packaging.python.org/en/latest/discussions/install-requires-vs-requirements/) · [pip repeatable installs](https://pip.pypa.io/en/stable/topics/repeatable-installs/) · [pip secure installs](https://pip.pypa.io/en/stable/topics/secure-installs/) · [pyside6-deploy reference](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html)

The current repository recipe selects Python 3.13.17 x64, PySide6 6.12.0, Nuitka 4.3.4, ordered-set 4.1.0, and zstandard 0.25.0. These are exact-version pins, **not hash locks**. The build script now asks pip for an installation report and records each resolved package name, version, and SHA-256 archive hash in `BUILD-DEPENDENCIES.json`, alongside the Windows/MSVC/SDK identities. This evidence-capture code has not yet run on Windows. A pip installation report is **not a lock file** and cannot be fed back into pip as an install plan. It also does not establish the inputs installed in a separate temporary PEP 517 build environment; those build requirements must be pinned and captured separately or managed in the main environment. The project still needs a Windows-specific hash-checked lock before calling the build inputs locked. Use a clean Windows build runner with the required MSVC `dumpbin` available through the Visual Studio environment. Build only trusted source: Qt notes that Nuitka analysis can execute/import application code during packaging. Pinned inputs make the build environment repeatable; they do **not** prove byte-for-byte reproducible artifacts. That needs its own Windows experiment. [pip installation report reference](https://pip.pypa.io/en/stable/reference/installation-report/) · [pip build-system isolation](https://pip.pypa.io/en/stable/reference/build-system/) · [pip repeatable installs](https://pip.pypa.io/en/stable/topics/repeatable-installs/) · [pyside6-deploy reference](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html) · [Nuitka deployment](https://nuitka.net/doc/user-manual.html)

The current [PySide6 6.12.0 release metadata](https://pypi.org/pypi/PySide6/6.12.0/json) declares dependencies on `PySide6_Essentials` 6.12.0, `PySide6_Addons` 6.12.0, `PySide6_WebEngine` 6.12.0.140, and `PySide6_Pdf` 6.12.0.140. The four direct pins in `requirements/windows-build.txt` therefore do not describe the complete resolver input set. Collect the actual Windows 3.13 x64 wheel names, versions, and SHA-256 hashes from the existing build host; include all resolved transitive build dependencies in the lock. The installed resolver set also does not predict which Qt modules Nuitka places in the app `.dist`, so inspect that actual directory before the licensing and size review. Do not remove a declared PySide dependency based only on metadata; validate any selective installation approach with `pyside6-deploy` on Windows.

## Signing boundary

Keep Authenticode signing as a separate release step after packaging and artifact inspection. Microsoft documents SignTool for signing and verification, with SHA-256 file digests and RFC 3161 timestamping. Keep signing credentials out of source control and ordinary build artifacts; the build job should produce an unsigned candidate, and a protected release job should sign and verify the final executable (and installer if one is later added). This separation is a release-process recommendation; Qt's deployment documentation does not perform or promise signing. [Microsoft SignTool](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool) · [Authenticode timestamps](https://learn.microsoft.com/en-us/windows/win32/seccrypto/time-stamping-authenticode-signatures)

## Windows validation still required

No Windows packaging result is established by this research. Qt's current platform support documentation specifies Windows 10 version 1809 or later and Windows 11 for x64. Validate on the target Windows version and architecture that the pinned environment builds successfully with MSVC tools; the ZIP starts on a clean machine without a developer Python/PySide installation; Qt plugins, DLLs, icons, and other resources resolve; and Frontdoor can complete FreeCAD discovery/download, isolated-profile setup, launch, failure recovery, and clean shutdown. Separately verify the signed release artifact and its timestamp. Decide whether SmartScreen behavior and a native installer are release requirements. Until these checks pass, call the package plan **unverified**, not a Windows-tested release candidate.

## Licensing notes

Qt for Python's Community Edition is offered under LGPLv3/GPLv3; Qt's own licensing page also notes that individual modules have different license availability. Inspect the actual Qt/PySide modules in the standalone folder and review the relevant license text, relinking/source and notice obligations for the intended distribution. Nuitka documents an AGPLv3 license with a runtime exception in its source distribution; verify the exception for the selected version. These are flags for release review, not a legal conclusion.
