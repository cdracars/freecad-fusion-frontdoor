## Current work

- **Highest-risk finding:** `installer._is_expected_publisher` accepted a publisher when the expected company name appeared anywhere in the subject. New regression tests reproduced the spoof and mismatched-CN/O cases. Validation now parses the subject and requires exact matching `CN` and `O`, with case folding and the documented optional leading `The`.
- The setup confirmation now names the expected publisher; installation docs were corrected to reflect the existing confirmation dialog and the exact signer check.
- Local verification after the license change at that point: 21 unit tests passed with `PYTHONPATH=src`; Python compilation, deterministic workbench payload generation, and `git diff --check` passed. Tests cover the ZIP resource staging fallback with mocked `importlib.resources`; they do not prove behavior in a frozen Windows package. A plain `python3 -m unittest` from the repo root does not include `src/` on `sys.path`, so it fails to import the package unless the project is installed or `PYTHONPATH=src` is set. These checks are not Windows certificate-verification or packaging evidence.
- Fusion launch status now uses a per-launch token passed only to the Fusion profile. The Frontdoor workbench writes an atomic marker after activation and task-surface display; the desktop app waits up to 90 seconds for that exact marker and says only “Frontdoor workbench loaded.” This does not certify every modeling command or the navigation add-on. Full FreeCAD status remains explicitly unconfirmed. Unit tests cover marker validation and token isolation, but this handshake has not yet run inside Windows FreeCAD.
- Independent review found no remaining bypass for the recorded publisher subject format. It also identified that the subject parser is intentionally partial and the actual certificate still needs a post-change Windows run. Follow-up review found the readiness signal is token-isolated and flagged the original status wording as broader than the evidence; the UI/spec wording is now narrowed to workbench load.
- The local packaging scaffold uses Qt's official `pyside6-deploy` in standalone mode, pinned exact versions (Python 3.13.17 x64; PySide6 6.12.0; Nuitka 4.3.4; ordered-set 4.1.0; zstandard 0.25.0), and a generated ZIP resource for the Frontdoor workbench. `scripts/build_windows.ps1` creates an isolated build venv, checks for Visual Studio `dumpbin`, refuses dirty-source builds and unowned output directories, creates an unsigned ZIP with build metadata/notices, and emits a SHA-256 sidecar. Inputs are not yet hash-locked; artifact output, clean-machine start, and included Qt runtime contents remain unverified on Windows. See [packaging research](../research/windows-pyside6-packaging.md).
- PyPI's PySide6 6.12.0 metadata declares Essentials, Addons, WebEngine 6.12.0.140, and Pdf 6.12.0.140 dependencies; the current four direct pins are not the complete resolver set. Record the actual Windows Python 3.13 x64 resolved wheels and hashes, then inspect the generated `.dist` for the Qt modules actually bundled. Do not change dependencies based on metadata alone; the existing Windows build host is required to validate the resolver and app output.
- The generated `pysidedeploy.spec` is local build state and intentionally excluded from the preview artifact to avoid leaking machine paths. The package notice calls for checking the actual included Qt modules and their license obligations before distribution. This is not a legal determination.
- In response to the user's selection, the project now uses MIT for its own code, declares that in Python packaging metadata, and stages the license into the Windows ZIP. This does not cover Qt/PySide or the separate add-on; inspect the exact Qt bundle and complete its licensing review before distributing the app.
- After the licensing change, all 21 unit tests, Python compilation, and `git diff --check` pass; an independent reviewer found no metadata/notice mismatch. A local wheel build was attempted but stopped before the project build because the environment could not resolve the package index to download the required setuptools 77.0.3; this is unverified packaging, not a successful wheel build.
- The launch handshake now carries a monotonic launch-request timestamp and records elapsed time at the Frontdoor task-surface show/raise call. If `FRONTDOOR_PERF_LOG` is set, the desktop app appends a local JSONL record; no log is written by default. The capture procedure is in [Windows performance validation](windows-performance-validation.md). This prepares a repeatable startup estimate but does not constitute a Windows baseline or measure core modeling operations.
- The startup metric is specifically launch-request to task-surface show/raise calls; it does not prove that Qt painted the panel or that the UI is interactive. A separate [FreeCAD macro](../tests/frontdoor_core_performance.FCMacro) measures representative core operations' model-update and recompute durations and checks resulting solids. Neither capture path has been run on Windows yet.
- Five new profile/install ownership regression tests verify creation and reuse of Frontdoor-owned profiles, refusal to adopt unmarked user data, refusal to claim populated unowned install directories, and correct installing-marker creation. They preserve existing files in the test cases; actual Windows filesystem and installer behavior remains to be verified.
- Added `.github/workflows/windows-tests.yml`, a read-only-permission Windows hosted CI workflow for Python 3.12 and 3.13. The latest run, [43456810071](https://github.com/cdracars/freecad-fusion-frontdoor/actions/runs/43456810071) on `5f40dd3`, completed successfully in both matrix jobs: package build/install, unit tests, compileall, and whitespace checks all passed. This is hosted Windows Python/package evidence, not evidence for the frozen desktop ZIP or FreeCAD GUI.
- Latest local verification: all 38 unit tests pass in the project virtual environment; Python compilation and `git diff --check` pass. These checks do not replace the pending frozen Windows build, GUI workflow, or startup/performance samples.
- **Installed-version reporting fix (2026-11-13):** independent review found that setup recorded the GitHub release tag when an installer returned success and a `FreeCAD.exe` existed, without confirming that the binary had actually updated. The install spec now requires a runtime version check. Setup queries the adjacent `FreeCADCmd.exe` first and falls back only to the other supported location inside the same install tree, using a temporary profile under the Frontdoor data root before and after an install/update. A mismatch raises a retryable error before the managed marker is rewritten. Regression tests cover both executable layouts with conflicting command versions, profile isolation, out-of-tree rejection, mismatch handling, and preservation of the old marker. The complete local suite now has 38 passing tests; Windows-specific command output and live-update behavior remain unverified.
